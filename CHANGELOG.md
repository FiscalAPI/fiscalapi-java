# Changelog

Cambios del SDK y notas de comportamiento del API de FiscalAPI que afectan a quien usa el SDK.

## [Sin publicar]

### Cambios incompatibles (BREAKING)

- Se eliminan `Person.getCapitalRegime()` y `Person.setCapitalRegime(String)` (estaban `@Deprecated`): el API no tiene régimen de capital, ignoraba el valor y nunca lo devolvía. El código que los llama deja de compilar: quite esas llamadas y envíe la razón social sin régimen de capital con `setLegalName`.
- El API deja de devolver `stripeCustomerId` y `subscriptionStatus` en las personas (`/api/v4/people` y la persona de las reglas de descarga): eran datos internos de Stripe. Este SDK nunca los modeló en `Person` (estaban comentados y se quitan), así que el código que usa el modelo no cambia; si su integración los lee de la respuesta JSON cruda, quite esa lectura: el campo ya no llega.
- Se elimina la clase `com.fiscalapi.common.StripePaymentMethodDto` (`stripeId`, `stripeCustomerId`, `brand`, `last4`, `expMonth`, `expYear` y demás datos de tarjeta): modelaba los métodos de pago de Stripe, que el API retiró en agosto de 2026, y ningún servicio del SDK la usaba. El código que la importa o la instancia deja de compilar: quite el `import com.fiscalapi.common.StripePaymentMethodDto;` y esos usos; el API no expone métodos de pago ni datos de Stripe que la reemplacen.

### Modelo `Person`

- Nuevos miembros:
  - `phoneNumber`: lo aceptan la creación y la actualización de personas.
  - `country`: país de residencia fiscal expandido (solo lectura).
  - `balances`: saldos por tipo de crédito (`CreditBalance`: `creditType` y `available`, solo lectura). Solo aparecen los tipos que la persona ha tenido; un tipo ausente tiene saldo 0, y `creditType` es `Integer` para conservar un tipo que el SDK no conoce.
  - `isOwner`: `true` si la persona es el owner de su tenant (solo lectura).
  - `validTo` (`LocalDateTime`, `getValidTo()`): fin de vigencia de la persona (solo lectura: se puebla al deserializar y no se envía). La asigna el API; casi siempre es `null` y es informativa (no limita el timbrado ni el acceso al API).
- `password`: requerida al crear; al actualizar, `null` o vacía conserva la contraseña actual. El API nunca la devuelve.
- `userTypeId`: `"C"` (cliente, el valor por omisión al crear) o `"U"` (usuario). `"T"` (tenant) solo llega en respuestas: el API lo rechaza al crear y al actualizar solo lo acepta si la persona ya es `"T"`.
- Se quitan los campos comentados `twoFactorEnabled`, `stripePaymentMethodId`, `stripePaymentMethod`, `stripeCustomerId` y `subscriptionStatus`, que el API ya no devuelve (el comentado `validTo` pasa a ser miembro real).

### Notas del API (sin cambio de forma en el SDK)

- `Person.taxPassword` es la contraseña de la llave privada (.key) que la persona guarda en su perfil; el API no la usa para sellar (al timbrar usa la contraseña de los certificados registrados o la de `taxCredentials`). Solo la reciben con valor la propia persona y el owner del tenant; los demás reciben `null`. Al actualizar, `null` la conserva (el SDK no envía los `null`) y `""` la borra.
- `ValidationFailure.attemptedValue` (y el placeholder `PropertyValue` de `formattedMessagePlaceholderValues`): en un 400 de validación, el valor de un secreto (contraseñas, códigos, tokens, archivos y contraseñas de CSD/FIEL) llega enmascarado como `"[masked: n]"` (`n` es su longitud), o `"[masked]"` si la falla es de un objeto o una lista que lo contiene.
- `TaxCredential.password` solo se exige en la llave privada (.key); en el certificado (.cer) el API no la usa.
- `TaxFile.tin` es opcional en `getTaxFileService().create()`: si es `null` o vacío, el API usa el RFC de la persona. Si se envía, debe ser el RFC de la persona (sin distinguir mayúsculas); si no, el API responde 400 con la falla en `Tin` (después de comprobar que puede gestionar los certificados de la persona; si no, 403). El API no guarda el valor enviado: el `tin` del archivo siempre es el RFC de la persona.
- Las personas ya no traen `stripeCustomerId` ni `subscriptionStatus` (datos internos de Stripe). `validTo` y `committedBalance` son de solo lectura: el API los ignora al crear o actualizar. `committedBalance` es un campo heredado que el API ya no calcula y siempre vale 0; para el saldo use `availableBalance`, `availableValidationBalance` o `balances`.
- Personas: `getPersonService().create()` y `getPersonService().update()` con un correo que ya pertenece a otra persona, de esta o de otra cuenta (se compara sin distinguir mayúsculas ni los espacios de los extremos), responden 400 de validación con la falla en `Email` y el mensaje `The email is already registered.` (en el SDK, `getSucceeded()` es `false` y `getDetails()` vale `"Email: The email is already registered."`). Antes respondía otro 400 (una falla de Identity o el genérico `A record with the same unique values already exists.`). Al actualizar, el correo actual de la persona no cuenta como repetido. El API guarda el correo sin los espacios de los extremos.
- Personas: `getPersonService().update()` y `getPersonService().delete()` pueden responder 409 con `details` `The person was modified by another request (for example, a failed sign-in). Reload it and try again.` (en el SDK, `getHttpStatusCode()` 409 y ese texto en `getDetails()`) si otra petición modificó a la persona mientras se procesaba: cuenta cualquier escritura a la persona, por ejemplo un inicio de sesión con su correo (exitoso o fallido) o un cambio en su suscripción. No se guarda nada: vuelva a consultar la persona y repita la llamada. Antes la escritura se guardaba igual y podía deshacer el cambio de la otra petición (el bloqueo de la cuenta por intentos fallidos o la sesión recién iniciada). `PATCH /api/v4/people/{id}`, que este SDK no usa, responde el mismo 409.
- Personas: `getPersonService().create()` y `getPersonService().update()` validan el correo y la contraseña con las reglas de Identity antes de guardar. Un correo con caracteres fuera de `a-z`, `A-Z`, `0-9` y `-._@+` (por ejemplo `ñ`, una vocal acentuada, un apóstrofo o un espacio intermedio) responde 400 de validación con la falla en `Email`, `errorCode` `InvalidUserName` y el mensaje `The email contains characters that are not allowed: 'ñ'. Allowed characters: abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789-._@+` (con los caracteres rechazados entre comillas). Una contraseña que no cumple las reglas (al menos 6 caracteres, con una mayúscula `A-Z`, una minúscula `a-z`, un dígito `0-9` y un carácter que no sea letra ni dígito; las letras con acento y la `ñ` no cuentan como mayúsculas ni minúsculas) responde una sola falla en `Password` con el mensaje `Password must be at least 6 characters long and contain at least one uppercase letter (A-Z), one lowercase letter (a-z), one digit (0-9) and one character that is not a letter or a digit. Letters with accents and ñ are not uppercase or lowercase letters for this rule.`, el código del primer requisito que no se cumple en `errorCode` (p. ej. `PasswordTooShort` o `PasswordRequiresUpper`) y `attemptedValue` `null` (en el SDK, `getSucceeded()` es `false` y `getDetails()` trae la falla con el campo). Antes, al crear, esos valores llegaban a Identity y la falla traía el código en `propertyName` (`InvalidUserName`, `PasswordRequiresUpper`…) con el texto de Identity (p. ej. `Username '…' is invalid, can only contain letters or digits.`) (en el SDK, `getDetails()` empezaba con `InvalidUserName:` y ahora con `Email:`); una contraseña corta como `abc` daba dos fallas (`MinimumLengthValidator` y `PredicateValidator`), y al actualizar el API guardaba un correo con `ñ` o una contraseña como `Ñandú12!` (200). Si aun así `getPersonService().create()` falla en otra validación de Identity, la falla trae en `propertyName` el campo del request (`Email` o `Password`) y el código de Identity en `errorCode`.
- Facturas (`getInvoiceService().create()`): con una moneda extranjera (`currencyCode` distinto de `MXN` y de `XXX`), `exchangeRate` 0 o negativo responde 400 de validación con la falla en `ExchangeRate` y el mensaje `If the currency is different from MXN, you must specify the exchange rate of the day of the transaction.` (en el SDK, `getSucceeded()` es `false` y `getDetails()` trae la falla con el campo); antes pasaba la validación del API. Con `MXN` sigue siendo exactamente 1. El complemento de pagos sigue la misma regla en el tipo de cambio del pago (`complement.payment.exchangeRate` frente a `complement.payment.currencyCode`): con `MXN`, exactamente 1 (si es `null`, el API usa 1); con otra moneda, mayor que 0. Si no, responde 400 de validación con la falla en `Complement.Payment.ExchangeRate` (mensaje `If the currency is MXN, you must specify the exchange rate equal to 1` o el de moneda extranjera); antes llegaba al PAC, que lo rechazaba, o el pago salía con totales en 0.
- Cambios del API en los endpoints de cuenta, que este SDK no usa (se autentica con API key), así que no le afectan: `POST /api/v4/account/register` y `POST /api/v4/account/info` con un correo que ya pertenece a otra persona responden 400 de validación con la falla en `Email` (`NewEmail` en `info`) y el mensaje `The email is already registered.`; `POST /api/v4/account/change-password` con la contraseña actual incorrecta responde 400 de validación con la falla en `CurrentPassword` (`errorCode` `PasswordMismatch`, mensaje `Incorrect password.`); en general, las fallas que vienen de Identity en `account/change-password`, `account/info`, `account/reset-password` y `account/confirm-email` traen en `propertyName` el campo del request que las causó (`CurrentPassword`, `NewPassword`, `NewEmail`, `ResetCode` o `Code`) y el código de Identity en `errorCode` (`PasswordMismatch`, `InvalidToken`, …), en lugar del código como `propertyName`; `POST /api/v4/account/refresh` con un refresh token vencido responde 401 `Invalid refresh token` en lugar de emitir otro (con uno vigente devuelve el mismo token), así que una sesión iniciada con `account/login` solo se puede renovar hasta 7 días después del login.
- Facturas (`getInvoiceService().create()`): con `currencyCode` `XXX` (facturas de pago y de traslado), un `exchangeRate` distinto de 1 y de 0 responde 400 de validación con la falla en `ExchangeRate` y el mensaje `If the currency is XXX, the exchange rate does not apply: omit it (or send 1 or 0).` (en el SDK, `getSucceeded()` es `false` y `getDetails()` trae la falla con el campo); antes, con un valor mayor que 1 lo rechazaba el PAC (CFDI40116 en un ingreso, CRP20109 en un pago) y con uno entre 0 y 1 o negativo se timbraba ignorándolo. Con 1 (si es `null`, el API usa 1) o 0 se sigue timbrando, sin `TipoCambio` en el XML.
- Facturas de pago (`getInvoiceService().create()` con `complement.payment`): la moneda del pago (`complement.payment.currencyCode`) y la de cada factura pagada (`currencyCode` de cada `PaidInvoice`) se validan contra el catálogo c_Moneda del SAT, escritas tal cual: si se omiten, no están en el catálogo (también en minúsculas, como `mxn`) o son `XXX`, responde 400 de validación con la falla en `Complement.Payment.CurrencyCode` o en `Complement.Payment.PaidInvoices[n].CurrencyCode` (`n` = posición, desde 0) con el mensaje `Please use the SAT catalog values: …`, `The currency of a payment or of a paid invoice cannot be XXX.` o el de campo vacío (en el SDK, `getSucceeded()` es `false` y `getDetails()` trae la falla con el campo); antes llegaban al PAC, que las rechazaba (CFDI40113, CRP20213 o CRP20236). La moneda de la factura de pago (`currencyCode`) debe ser `XXX`: con otra, 400 de validación en `CurrencyCode` con `The currency of an invoice with the payment complement must be XXX.` (antes, el PAC respondía CRP20104). El valor por omisión de `Invoice.currencyCode` es `MXN`: en una factura de pago asígnele `XXX`. Una factura sin `currencyCode` responde una sola falla en `CurrencyCode` (antes, dos).
- Factura global (`getInvoiceService().create()` con `globalInformation.year`): el año acepta el de la fecha de la factura (`date`) y los 5 anteriores, como el SAT (con fecha en 2026, de 2021 a 2026); antes solo el año en curso o el anterior, y por ejemplo 2021 a 2024 respondían 400 aunque el SAT los timbra. Fuera de ese rango responde 400 de validación con la falla en `GlobalInformation.Year` y el mensaje `Year must be the year of the invoice date (2026) or one of the 5 previous years.` (con el año de la fecha) (en el SDK, `getSucceeded()` es `false` y `getDetails()` trae la falla con el campo).
- Más cambios del API en los endpoints de cuenta, que este SDK no usa: `POST /api/v4/account/register` (`Email`, `Password`), `POST /api/v4/account/info` (`NewEmail`, `NewPassword`), `POST /api/v4/account/change-password` y `POST /api/v4/account/reset-password` (`NewPassword`) aplican las mismas reglas de correo y contraseña que las personas (400 con `InvalidUserName` o con la falla única de la contraseña); antes `register` creaba la cuenta con un correo con `ñ` o una contraseña como `Ñandú12!`. `reset-password` valida la contraseña nueva antes del código (con las dos inválidas, la falla es la de `NewPassword`). En `account/info`, `CurrentPassword` ya no se valida con las reglas de formato (una incorrecta responde `PasswordMismatch` en `CurrentPassword`) y es obligatoria cuando viene `NewPassword`: sin ella, 400 de validación en `CurrentPassword` con `Current password is required to set a new password.` (antes, el mismo texto en un 400 sin campo).
